# ナレッジ記事テンプレート（Markdown・既定）

`<…>` を差し替えて使う。**外枠（frontmatter + `## TL;DR`）は共通・必須**、本論は記事の性質に応じて **型 A（トラブル型）** / **型 B（設計判断・比較型）** / **型 C（技術解説・仕組み型）** の 3 つから選ぶ。

| 型 | どんな知見か | 本論の見出し |
|---|---|---|
| **型 A：トラブル型** | 遭遇したエラー・バグ・落とし穴と対処 | `遭遇した問題` → `原因` → `解決` |
| **型 B：設計判断・比較型** | トレードオフ・選択肢の比較・設計指針 | `背景・射程` → `判断軸・比較` → `指針` |
| **型 C：技術解説・仕組み型** | 言語機能・API・内部動作など「技術的にこういうもの」の整理 | `概要・対象` → `仕組み・仕様` → `使いどころ・注意点` |

---

## 型 A：トラブル・ハマりどころ型

遭遇したエラー・バグ・非自明な挙動と解決策を残すとき。

```markdown
---
title: <結論を言い切る簡潔なタイトル（プレーンテキスト）>
tags: [<tech>, <topic>, ...]
---

## TL;DR

- 結論・解決策を箇条書きで先に（2〜5 行）。

## 遭遇した問題

- 何が起きたか。再現条件・環境（バージョン等）を残す。

## 原因

- なぜそうなるか。

## 解決

- どう直したか。

```ts
// 最小再現に絞ったコード。NG 例と OK 例を併記すると後で役立つ。
```

## まとめ

<!-- 短い記事（目安 100 行未満）なら省略し、TL;DR に集約してよい -->

- 要点を 1〜3 行で。

## 参考

<!-- 出典があるときのみ記載。必ず Markdown リンク形式で統一する -->

- [タイトル](https://example.com)
```

## 型 B：設計判断・比較型

設計トレードオフ、パターンの比較、複数の選択肢からどれを選ぶかを残すとき。

```markdown
---
title: <結論や判断軸を言い切る簡潔なタイトル（プレーンテキスト）>
tags: [<tech>, <topic>, ...]
---

## TL;DR

- 結論・判断基準を箇条書きで先に（2〜5 行）。

## 背景・射程

- どんな判断・迷いを扱うか。対象外があれば明記する。

## 判断軸・比較

- 選択肢の比較表、メリデメ、トレードオフなど（見出し名は内容に合わせて調整可）。

```ts
// 共通ボイラープレートは省き、構造の差分が分かる最小コードに絞る。
```

## 指針

- 実務でどう選び分けるか。

## まとめ

<!-- 短い記事（目安 100 行未満）なら省略し、TL;DR に集約してよい -->

- 要点を 1〜3 行で。

## 参考

- [タイトル](https://example.com)
```

## 型 C：技術解説・仕組み型

「〇〇とは何か」「どういう仕様・内部動作になっているか」といった、技術仕様や概念の解説を残すとき（例：`const fn`、`Pin`、ライフタイム注釈、`matches!`、`@discardableResult` など）。

```markdown
---
title: <対象と本質を言い切る簡潔なタイトル（プレーンテキスト）>
tags: [<tech>, <topic>, ...]
---

## TL;DR

- 何をするものか・本質を一言ずつ箇条書きで先に（2〜5 行）。

## 概要・対象

- 扱う機能・概念の定義と射程。対象バージョン・環境を残す。

## 仕組み・仕様

- 内部動作・ルール・構文・代表的なコード例。

```ts
// 挙動がひと目で分かる最小コード。
```

## 使いどころ・注意点

- できること / できないこと、ハマりやすい制約や例外。

## まとめ

<!-- 短い記事（目安 100 行未満）なら省略し、TL;DR に集約してよい -->

- 要点を 1〜3 行で。

## 参考

- [タイトル](https://example.com)
```

## 守るルール（検索性・表示崩れ防止）

### frontmatter とファイル名
- **`title`**：プレーンテキストで書く。バッククォート（`` ` ``）や `"React: "` のような技術プレフィックス、末尾「〜で」の尻切れ表現は避ける。
- **`tags`**：**小文字英語ケバブケース・1 行配列**、目安 **3〜6 個**（技術名 1〜2 個 ＋ トピック 2〜4 個）。既存タグ（`/api/tags.json`）を優先して再利用し、表記ゆれや日本語タグを避ける。
- **ファイル名**：新規記事は **小文字英語ケバブケース**（例：`abort-controller-fetch-race.md`）。半角スペースは禁止。

### Markdown / Docusaurus 表示崩れ防止
- **太字 `**` と括弧の境界**：日本語文字と括弧（`「」` `（）` `()`）や `` ` `` の境界に `**` を隣接させない（CommonMark の仕様で `**` が生表示される）。括弧を太字の外に出す（例：`「**...**」`、`**自己参照**（self-referential）`）。
- **ハードラップ禁止**：段落の途中で手動改行を入れない（表示時に不自然な空白が入る）。
- **コードブロック**：必ず言語を指定する（図やツリーは `text`）。
- **`<...>` 欠落確認**：Issue やテキスト変換を経由した場合、`<T>` や `<Component />` が欠落していないか確認する。
- **参考リンク**：裸 URL ではなく `[タイトル](URL)` で書く。

### 日本語・汎用化ガイドライン
- 文体は **常体（「だ・である」調）** で統一する。
- 和欧間スペースなどの細かいタイポグラフィは厳格に縛らず、1 記事内で揃っていればよい（括弧は全角 `（）` 推奨）。
- 英語・略語の過度な直混ぜや造語を避け、日本語で一読して意味が通る表現にする。
- 執筆時の会話ログ（「質問者の〜」「Gemini に調べさせた」）や、特定プロジェクト固有の型名・Issue 番号・PR diff 行数は汎用表現へ置き換える。

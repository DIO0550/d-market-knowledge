コンテナの基本

イメージとコンテナ

実行のもとと、実行する環境を区別する。

アプリを動かすには、プログラムだけでなく、実行環境や必要なファイルも揃える必要があります。これらをまとめたものが、 イメージ（Image） です。

イメージをもとに作られる実行環境を、 コンテナ（Container） と呼びます。同じイメージから、複数のコンテナを起動できます。

用語の補足

イメージは実行のもとになるもの。コンテナは、そのイメージから作る個々の実行環境です。

操作を、対象と結び付ける

コマンドは「何をもとに、何をするか」で整理できます。イメージを作る操作と、コンテナを起動する操作は別です。

コマンドと操作する対象
コマンド 対象 結果
docker build ソースと Dockerfile イメージを作る
docker run イメージ コンテナを作って起動
docker push イメージ レジストリへ送る

送るのは、イメージ

別の場所でアプリを動かすときは、イメージを共有し、その場所で新しいコンテナを起動します。動いているコンテナそのものを送るわけではありません。

ポートを公開して接続する

「動いている」と「接続できる」は、別の確認。

コンテナ内でアプリが動いていても、ホストから接続できるとは限りません。ホスト側のポートとコンテナ側のポートを対応付けて、接続先を用意します。

起動コマンドを読む

my-app:v1 は使用するイメージ、demo はコンテナの名前です。-p の指定は、ホスト側のアドレス、ホスト側のポート、コンテナ側のポートの順に並びます。

ポートに関する設定の違い
設定 役割
EXPOSE アプリが使用するポートの情報を示す
docker run -p ホスト側とコンテナ側のポートを対応付けて公開する

情報と公開設定を区別する

Dockerfile に EXPOSE を記述しただけでは、ホスト側へのポート公開は行われません。実際の公開には -p などの指定が必要です。

前提：イメージは作成済み。アプリはコンテナ内の 0.0.0.0:8080 で待ち受けます。掲載例は実行未検証です。

イメージを共有して動かす

同じアプリを、別の場所で新しく起動する。

ローカルで作ったアプリを別の場所で動かすときは、イメージをレジストリへ送ります。配備先では、そのイメージを取得し、新しいコンテナを起動します。

この流れを「作成」「保存・共有」「起動」に分けると、どの対象がどこへ渡るのかを整理できます。

レジストリとは

イメージを保管して共有する場所です。Google Cloud では Artifact Registry などを利用します。

実行環境は、それぞれ独立する

同じイメージを使っていても、コンテナは別々の実行環境です。一方を停止したという理由だけで、もう一方も停止するわけではありません。

共有するものと、別々に動くもの

共有するのはイメージです。コンテナは各環境で作って動かします。基本の関係はを参照してください。
